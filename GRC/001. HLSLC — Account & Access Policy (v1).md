HLSLC — Account & Access Policy (v1)

Role: GRC Audience: IT Ops (this document is the standard the AD build will implement) Status: v1 — intentionally minimal; complexity added in later revisions

1. Scenario

HomeLab Simulated Logistic Company (HLSLC) is a small, newly-modeled freight/logistics company about to have its first Active Directory environment built. Before any account is created, GRC is establishing the baseline standard IT Ops will build against — the goal is a documented policy to implement, not accounts created ad hoc and explained afterward.

2. Business problem

Without a written standard in place first, account creation defaults to whatever seems reasonable in the moment — inconsistent naming, inconsistent access levels, no defined process for who approves what, and no plan for removing access when it's no longer needed. Each of those individually is a small gap; together, they're how organizations end up unable to answer "who has access to what, and why" — usually the first question in any real audit.

3. Access risk

This policy exists specifically to prevent, from day one rather than after the fact:

Excessive access — accounts provisioned with more than their role needs, because no standard defined what "enough" looks like.
Undocumented justification — access granted with no record of why, making later review guesswork.
Inconsistent offboarding — access outliving the need for it, simply because no process required someone to remove it.
Self-approval / no segregation of duties — access granted without a second party checking it against the role.
4. What we built
4.1 Account naming convention
Username: first initial + last name, lowercase (e.g., jsmith).
Administrative accounts append -adm and are issued only where a role requires privileged actions distinct from daily use (e.g., IT Manager). No account performs daily-use work from its -adm identity.
4.2 Password requirements
Minimum 12 characters. No forced complexity rules (no mandatory mix of symbol/number/case) — length is the primary control, consistent with current NIST 800-63B guidance rather than older complexity-driven policy.
No mandatory periodic rotation. Passwords are changed only on suspicion of compromise, or immediately following any shared/temporary credential handoff (e.g., new-hire initial password).
Account lockout after 5 failed attempts within 15 minutes.
Multi-factor authentication required for all administrative (-adm) accounts. Not yet required for standard accounts in v1 — flagged as a likely v2 addition once MFA infrastructure exists in the lab.
4.3 Least privilege statement

Access is granted only to the minimum systems and data required to perform the assigned job function, and is reviewed periodically to confirm it remains necessary. Access is never granted "in case it's needed later."

4.4 New-hire checklist
Manager submits an access request: role, department, systems needed, and business justification.
Manager approves. If the request includes Finance-Data-Access, the Accounting Manager (data owner) approves in addition to the requesting manager.
IT Ops provisions the account per §4.1, assigning only the requesting department's security group. Any additional group requires its own separate, justified request — it is never bundled in "to save time."
Credentials delivered securely; password must be changed at first login.
4.5 Offboarding checklist
Manager notifies IT Ops of the departure or role-change date in advance of the effective date, where possible.
IT Ops disables the account on the effective date. Disabling — not deletion — is the immediate action, to allow for any brief data/email handoff.
Account is removed from all security groups except a holding state pending final deletion.
Account is fully deleted after a defined retention window (30 days, v1 default), unless the departure is fixed-term/seasonal, in which case the disabled account may instead be retained for the following season per manager decision (see roster notes).
Roster and any relevant logs are updated with the date and reason.

Note: this differs slightly from how the lab's own internal test accounts (testuser, hydratest) were retired — those were deleted immediately with no retention window, because they held no data and had zero handoff consideration. That was the correct call for disposable test accounts specifically, not a deviation from this policy, which governs real personnel access.

5. Evidence

None yet — this document is the standard, not an implementation. Evidence (OU structure, group membership exports, screenshots) will be produced in the next entry, when IT Ops builds the AD environment against this policy.

6. Recommendation

Pass this document to IT Ops as the specification for the initial AD build: OUs per department, security groups per §4.1–4.3 conventions, and the roster (v1) as the account list to provision. Recommend IT Ops flag anything in this policy that proves impractical to implement exactly as written — that feedback becomes input to v2, rather than a silent deviation.
